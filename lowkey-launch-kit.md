**The strategic choice**

Give Lowkey a lasting identity: useful little tools from Shrinath. Make Owleye the current product people can discover through that work. This preserves Lowkey's usefulness for future projects without having to rebrand it each time.

Recommended positioning: **“Small tools for the things between idea and launch. Free to use. No account required.”**

Keep the existing “Small tools, quietly useful” headline if you like it. The more specific line belongs in founder-facing posts and curated collections. Lowkey can serve a broad audience while this launch campaign focuses on people building websites and small businesses.

Start with **Favigen** for website builders, then **Billbook** for freelancers and studios. My hypothesis is that these audiences overlap more with buyers of web analytics than people arriving solely to split a dinner bill. Validate that through actual referral and activation data. Supersplit can still grow Lowkey's broader audience; it serves a different immediate objective.

The path to test is: useful post → relevant tool → completed task → maker curiosity or a real analytics example → Owleye → first website sending events.

Your estimated $100–$200 annual infrastructure spend makes this a relatively small cash experiment. Protect your development time too: freeze new tool work through September 15, apart from bugs that prevent the advertised task. A free tool can be inexpensive to host and expensive to keep expanding.

Treat SEO as a longer-term possibility. An owned footer link does not establish an acquisition channel, and multiplying links does not establish ranking value. Google specifically warns about links and low-value content made primarily to manipulate rankings. Keep genuine maker links and invest in tools people independently recommend. [Google's link-spam policy](https://developers.google.com/search/docs/essentials/spam-policies#link-spam)

**Measure useful attention**

Your 1% idea is worth testing, with a defined denominator. If 10,000 Lowkey visits yield a 1% visit-to-Owleye rate, that is 100 Owleye visits. It is not 100 signups or customers. This is arithmetic illustrating your hypothesis, not a forecast.

Use two scorecards: Lowkey's usefulness, and the downstream product's acquisition. That lets a useful tool remain valuable even if its first audience does not immediately need analytics.

| Measure | Definition and interpretation |
| --- | --- |
| Task completion | The advertised result was successfully generated or saved. A button click alone is insufficient. |
| Tool conversion | Sessions with at least one successful task ÷ sessions that entered that tool, if the available session measurement supports this. Otherwise report starts and completions separately. |
| Owleye discovery | Relevant outbound clicks by tool and placement, plus campaign-tagged arrivals on Owleye. These counts can differ. |
| Owleye activation | A new customer site sends its first valid production event. Account creation and npm downloads are earlier signals. |
| Feedback | Specific friction and evidence that someone used the output for a real task. |

Proposed custom events, to implement and verify through Owleye: `tool_started`, `tool_completed`, `owleye_link_clicked`. Allow only fixed fields such as tool name, output format, and placement. For example, Favigen completion means the ZIP has been successfully generated; Billbook completion means the export is ready. Do not claim that the analytics SDK can confirm a user saved a file to disk unless that behavior is actually observable.

Do not include invoice contents, amounts, customer details, notes, secrets, filenames, or dynamic personal URLs in the event payload. Inspect automatic page paths and titles too. This is especially relevant to a tool collection that handles documents and credentials.

Owleye documents campaign capture as off by default. Use `captureCampaigns: true` when campaign attribution is wanted; keep full-query capture disabled. The documented campaign fields are `utm_source`, `utm_medium`, and `utm_campaign`, so use those rather than assuming `utm_content` will appear. Test a tagged arrival in the dashboard before relying on it. [Owleye SDK configuration](https://owleye.dev/docs/sdk/#configuration)

Example Lowkey campaign link: [September 8 Favigen post](https://lowkey.tools/favigen?utm_source=x&utm_medium=social&utm_campaign=lowkey_20260908_favigen).

Example Owleye referral link: [Owleye from the Lowkey footer](https://owleye.dev/?utm_source=lowkey&utm_medium=referral&utm_campaign=footer_202609).

Track Lowkey and Owleye as separate sites. Do not assume their privacy-preserving identifiers join into one person across domains. Use campaign arrivals and within-site progression for an aggregate view; report “unknown” where attribution is missing. An optional “How did you hear about us?” question can supplement that. Preserve privacy controls and do not fingerprint people to close the gap.

Offline activity, blocked requests, and privacy choices can make collected events an incomplete view of use. Make public claims about observed usage and include the measurement period. In a short launch window, a few visits should prompt conversations rather than a claim that one channel has won.

For the soft launch, a useful internal goal is 5–10 people attempting setup and at least three independent sites sending real events. These are suggested learning goals, not expected demand. Before the hard launch, resolve repeated installation blockers and test the advertised public path yourself.

If Lowkey gets impressions but few visits, improve the problem and demo. If people arrive but do not finish, fix the tool. If they finish but do not explore Owleye, test a better contextual example. If they reach Owleye but never send events, investigate positioning and onboarding before building more free tools.
